# P2.5 AXI-Stream + cross-layer DATAFLOW contract

## Deployment top

`srcnn_axis_dataflow_top` is the fixed-size deployment wrapper:

```text
AXI4-Stream input (65,025 x 32-bit words)
        |
        v
axis_to_scalar
        |
        v
Conv1 OC4 -> FIFO (pixel-major, 64 channels/pixel)
        |
        v
Conv2     -> FIFO (pixel-major, 32 channels/pixel)
        |
        v
Conv3     -> FIFO (pixel-major, 1 channel/pixel)
        |
        v
AXI4-Stream output (65,025 x 32-bit words)
```

The external image dimensions are compile-time fixed at `255x255`. One AXIS
beat carries the exact 32-bit representation of one `data_t`. Output `TKEEP`
and `TSTRB` are `0xF`; output `TLAST` is asserted only on word 65,024. The DMA
host must send exactly 65,025 input words with all four bytes valid and `TLAST`
on the final word. The hardware datapath consumes a fixed frame length and does
not branch on the incoming sidebands.

The top uses `ap_ctrl_hs` through AXI4-Lite. It has one additional `m_axi`
master named `model_mem`; the AXI4-Lite `model` register holds the physical
address of a contiguous model buffer in PS-accessible DDR.

## Runtime model buffer

The public repository does not contain the official course model. To avoid
hard-coding random test parameters, this checkpoint loads one contiguous model
buffer on every invocation. All 8,129 elements are copied into layer-owned
local arrays before the DATAFLOW region starts; no stage reads `model_mem`
during pixel processing. Its elements retain the frozen OIHW/O order:

| Offset | Count | Payload |
|---:|---:|---|
| 0 | 5,184 | Conv1 weights `[64,1,9,9]` |
| 5,184 | 64 | Conv1 bias `[64]` |
| 5,248 | 2,048 | Conv2 weights `[32,64,1,1]` |
| 7,296 | 32 | Conv2 bias `[32]` |
| 7,328 | 800 | Conv3 weights `[1,32,5,5]` |
| 8,128 | 1 | Conv3 bias `[1]` |

Total: 8,129 32-bit elements, or 32,516 bytes. In the fixed deployment build,
each element is the raw bit pattern of the configured `ap_fixed<32,24,...>`
value. If the course later requires weights compiled into ROM, only this model
loading boundary should change; the four-stage streaming core remains intact.

## Internal layout and storage

External Golden tensors remain CHW/OIHW/O. The single-channel input and output
are naturally row-major. Internal inter-layer streams are deliberately
pixel-major because Conv2 and Conv3 consume all channels of one spatial sample
together:

```text
(row 0, col 0, channel 0..C-1),
(row 0, col 1, channel 0..C-1), ...
```

No complete Conv1 or Conv2 feature map is allocated. Conv1 stores one incoming
row plus eight fixed row delays; Conv3 stores one 32-channel incoming row plus
four fixed row delays. Replicate-edge padding is generated by replaying the
first and last rows and clamping horizontal columns. This also covers a 1x1
frame without a special padding path.

## Verification and remaining gate

Mac host simulation compares the final stream output against the frozen OC4
pointer implementation for 1x1, 5x7, and 13x17 replicate-edge cases. Float is
bitwise identical and host `ap_fixed` is exactly identical. Word count,
`TKEEP`, `TSTRB`, and `TLAST` are checked.

This is a host-verified checkpoint, not a synthesized or board-verified claim.
Vitis 2026.1 must still run C simulation, C synthesis, RTL co-simulation, and IP
export. The first report must confirm the DATAFLOW processes/FIFOs, model-memory
interface, latency, timing, and resources before any further throughput pragma
is added. Official weights and course images are still required for the final
numeric-quality gate.

The Vitis script uses `srcnn_axis_dataflow_cosim_top` for the three small
regression frames, then opens a separate solution and exports only the fixed
`srcnn_axis_dataflow_top`. This prevents a nominal co-sim pass that never calls
the synthesized top and avoids impractical 255x255 RTL simulation time.

## RTL co-simulation isolation modes

The default testbench performs three top-level transactions in one simulator
run. If RTL co-simulation stops after transaction 1, define
`SRCNN_AXIS_DATAFLOW_TEST_CASE` in the **testbench compile flags** to isolate
the failure without changing the DUT:

| Value | Top-level calls | Diagnostic purpose |
|---:|---|---|
| 0 | 1x1, 5x7, 13x17 | Full regression (default) |
| 1 | 1x1 only | Smallest single transaction |
| 2 | 5x7 only | Tests the previously stalled second size directly |
| 3 | 13x17 only | Largest small-image transaction |
| 4 | 1x1, then 1x1 | Tests `ap_start`/`ap_done` restart independently of size |
| 5 | 1x1, then 5x7 | Tests restart together with a dimension change |

Run modes 1, 2, and 3 as separate RTL co-sim components or solutions first.
Interpret the results as follows:

- If mode 2 stalls by itself, the 5x7 DATAFLOW execution has a DUT/FIFO issue.
- If modes 1--3 pass but mode 4 stalls, the generated top or harness does not
  restart correctly between transactions.
- If mode 4 passes but mode 5 stalls, the failure is specific to changing the
  runtime dimensions between invocations.
- If every isolated mode passes but mode 0 stalls, preserve the logs and treat
  it as a multi-transaction co-simulation/harness problem; do not call it an
  arithmetic or Conv2 failure.

For the Tcl flow, set the environment variable of the same name before running
`run_axis_dataflow_hls.tcl`. In the Vitis Unified GUI, add
`-DSRCNN_AXIS_DATAFLOW_TEST_CASE=N` to the testbench C++ compile flags. Keep all
design sources, top function, part, clock, and numeric flags identical across
the runs.
